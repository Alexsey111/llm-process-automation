•	Вариант F — Процесс финансовой отчётности. Вход: текст расходного документа или счёта (например, заявка на расход или выписка). Выход: извлечение ключевых полей (сумма, дата, контрагент, назначение платежа), категория расхода, статус (например, «требует одобрения»/«оплачен»), следующая операция (например, оплатить/запросить уточнение), запись в журнал. Если LLM не может выделить поля (неполные данные) — confidence=low и escalate=true.

•	Вариант H — Медицинская или страховая triage. Вход: описание симптомов пациента или заявка на страховой случай. Выход: оценка срочности (urgent/normal), ключевые симптомы/детали, краткий статус (например, «нужна консультация врача»/«данные неполные»), предложение следующего шага (назначить приём/запросить доп. информацию), запись в журнал. Если информации мало или ситуация серьёзная — confidence=low и escalate=true.

Во всех этих примерах логика аналогична: входной текст преобразуется LLM в заданную JSON-схему (с нужными полями), затем проводится валидация/эскалация по правилам качества, и результат сохраняется (в БД или файл) для дальнейших действий. Такие кейсы позволят продемонстрировать универсальность подхода «вход → LLM (структурированный JSON) → контроль качества → действие» в разных предметных областях.


Да. Тогда я бы **не смешивал F и H в один бизнес-процесс**, а сделал их как два самостоятельных кейса на **одном техническом каркасе**. Это даже сильнее для портфолио: один engine → два разных business workflow.

При этом H предлагаю реализовать именно как **страховой triage**, а не медицинскую диагностику. Так мы демонстрируем автоматизацию высокорискового процесса без того, чтобы LLM принимала медицинское решение.

FastAPI + Pydantic здесь хорошо подходят: Pydantic-модели одновременно дают валидацию входа и JSON Schema/OpenAPI-схему. ([FastAPI][1])

Я бы не делал слишком много полей.

```json
{

  "document_date": "2026-09-18",

  "payment_due_date": "2026-09-25",
  "purpose": "консультационные услуги",

```

### Pydantic

```python
from datetime import date
from typing import Literal

from pydantic import BaseModel, Field


class FinancialExtraction(BaseModel):
    document_type: Literal[
        "invoice",
        "expense_request",
        "payment_order",
        "unknown"
    ]

    document_number: str | None = None
    document_date: date | None = None

    counterparty: str | None = None

    amount: float | None = Field(
        default=None,
        ge=0
    )

    currency: Literal[
        "RUB",
        "USD",
        "EUR",
        "GBP",
        "unknown"
    ]

    vat_rate: float | None = Field(
        default=None,
        ge=0,
        le=100
    )

    payment_due_date: date | None = None

    purpose: str | None = None

    confidence: Literal[
        "high",
        "medium",
        "low"
    ]

    missing_fields: list[str]

    next_action: Literal[
        "approve_payment",
        "request_clarification",
        "manual_review"
    ]

    escalate: bool
```

И здесь важно: **LLM не должна сама определять `escalate` как единственный источник решения**.

После неё Python дополнительно проверяет:

```python
if result.confidence == "low":
    result.escalate = True

if result.missing_fields:
    result.escalate = True
```

То есть:

```text
LLM recommendation
        ↓
Python deterministic rules
        ↓
final decision
```

Это существенно сильнее с точки зрения демонстрации AI automation.

# 4. Самое важное — системный prompt

Для F:

```text
Ты — модуль структурирования финансовых документов.

Твоя задача — извлечь информацию ТОЛЬКО из предоставленного текста
и вернуть результат строго по заданной JSON-схеме.

Правила:

1. Никогда не придумывай отсутствующие данные.
2. Не делай предположений о неизвестных значениях.
3. Если поле отсутствует, используй null.
4. Если обязательная информация отсутствует,
   добавь её название в missing_fields.
5. Если информации недостаточно для уверенного извлечения,
   установи confidence="low".
6. Не интерпретируй документ шире предоставленного текста.
7. Не принимай финансовых решений.
8. Верни только JSON.
9. Не добавляй markdown.
10. Не добавляй пояснения до или после JSON.

Допустимые значения confidence:
high, medium, low.

Допустимые значения next_action:
approve_payment,
request_clarification,
manual_review.
```

Температура:

```text
0.2
```

Для этого проекта я бы **не поднимал temperature вообще**.

Нам не нужна креативность.

Нам нужны:

```text
repeatability
+
extraction
+
classification
+
structured output
```

# 6. Валидация должна быть двухуровневой

Это один из главных моментов проекта.

### Уровень 1 — schema validation

```text
LLM
 ↓
JSON parsing
 ↓
Pydantic
```

Например LLM вернула:

```json
{
  "amount": "много"
}
```

Pydantic это отвергает.

---

### Уровень 2 — business validation

Даже валидный JSON может быть плохим.

Например:

```json
{
  "confidence": "high",
  "policy_number": null,
  "required_missing": ["policy_number"],
  "escalate": false
}
```

С точки зрения JSON это абсолютно валидно.

Но бизнес-логика говорит:

```text
missing required information
        ↓
escalate = true
```

И Python исправляет состояние.
